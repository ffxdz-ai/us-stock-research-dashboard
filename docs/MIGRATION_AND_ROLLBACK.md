# 迁移、持久化与回滚

## 版本与历史记录

- 本次新信号使用模型/政策 `2.1.0`，仿真政策 `simulation-1.0.0`。
- 旧报告、旧信号和原始数据不重算、不覆盖。它们缺少历史因子或快照时标记为不可重建。
- `signal_id` 由证券、策略、计划、信号时间、快照和版本的规范内容生成；同一条件重复运行幂等，不同版本或重新入场生成新标识。
- SQLite 迁移由 `scripts/simulation_ledger.py::migrate()` 幂等执行；发现比当前代码更新的 schema 会停止，而不是降级覆盖。

## 本地持久化

默认私有账本：`data/simulation_ledger.sqlite`。SQLite 使用 WAL、外键、唯一内容哈希和幂等事件键。运行前后应：

1. 停止所有写入进程。
2. 使用 SQLite backup API 或文件系统快照备份数据库及校验和。
3. 执行 `PRAGMA integrity_check`。
4. 运行一份固定 fixture，确认信号/事件/成交数量不重复且净值可对账。

`data/*.sqlite*` 已加入 `.gitignore`，避免账户或私有仿真明细进入公开 Git 历史。公开网页只允许导出聚合计数和不含账户信息的研究字段。

## GitHub Actions 持久化限制

GitHub 托管 runner 每次是干净环境。当前仓库没有配置一个经用户授权的私有耐久对象存储，因此本次没有把本地 SQLite 接入日报工作流，也没有声称跨日持久化已完成。Actions cache 不是账本数据库，制品也不适合作为无冲突的权威可写状态。

上线前应选择一种私有耐久方案：

- 私有对象存储保存加密 SQLite 快照，任务启动下载、校验版本和哈希，任务结束原子上传；
- 私有数据库/私有 Git 仓库保存事件日志，并用单写者锁避免并发任务；
- 保持前向仿真在本机/自托管 runner，GitHub Pages 只接收脱敏聚合结果。

无论选择哪种方式，都必须配置并发锁、恢复失败即停止写入、备份保留、加密密钥轮换和公开/私有数据分离。需要相应存储地址及 Secret 后才能做真实联调。

## 回滚步骤

1. 停止日报、Worker 实时提醒和任何仿真写入任务。
2. 保存当前数据库备份与 `git diff`，不要删除新格式历史。
3. 将运行配置切回上一版 `model_version` / `policy_version`，或切换到变更前 Git 提交。
4. 使用与旧代码兼容的独立数据库文件；不要让旧代码打开更新版 schema 后尝试覆盖。
5. 重新运行旧版确定性测试和公开档案校验。
6. 若仅回滚网页，可回滚 `docs/app.js`/`docs/live-quotes.js`，但保持新 JSON 字段；前端对缺失字段已有 fallback。

回滚不会删除 2.1.0 信号；恢复新版本时可继续从原 2.1.0 账本读取。

## 未校准阈值

以下均是工程默认值，不是历史最优参数：

- 最低因子覆盖率 0.80；
- 执行报价最大年龄 60 秒、未来容差 300 秒；
- 正式路径成本后 R/R 3:1；
- 单笔预估损失 0.5%、单票 10%、主题 25%、行业 20%、总止损风险 3%；
- 回撤 8% 降风险、12% 暂停、冷却 5 个交易日；
- 未知相关性和财报日期未知时风险乘数；
- 仿真手续费、滑点、点差、参与率与 TIF。

只有在冻结参数、时点正确、样本外且成本一致的验证后，才可决定是否调整。调整必须提升版本并保留旧实验记录。
